## 1. Executive Summary

NyayaDrishti-LM is a well-structured legal metrology compliance platform with a significant demo/mock architecture that is **intentionally and explicitly designed** to work at hackathon presentations. However, this same architecture creates several critical trust and integrity problems that must be understood clearly before the system can be considered trustworthy for real-world statutory enforcement.

**Overall Condition:** PARTIALLY WORKING — DEMO-RIGGED. The system is capable of genuine end-to-end processing for real images when the live backend is reachable and the pipeline adapters are loaded, but multiple fallback layers mask failures silently and serve synthetic data that can be indistinguishable from real results at the UI level.

**Most Serious Issues:**
1. **Silent mock promotion (P0-INT-001):** Any network error during live inspection silently promotes the session to MOCK mode, serving synthetic data as if it were real backend processing — with no officer-visible indicator change.
2. **Hardcoded demo credentials in frontend production code (P0-SEC-001):** `liveApi.ts:89` contains `password: "Officer@2026"` and username `inspector_rajesh` / `controller_south` in plaintext JavaScript.
3. **Backend fixture matching for named demo SKUs (P0-MOCK-001):** The `/api/v1/pipeline/execute/{image_id}` endpoint on the backend (server.py:762–778) matches uploaded images against Golden SKU fixture JSON files by fuzzy-comparing product_name, brand_name, and inspection_number. If a match is found AND `is_explicit_demo` is true, it returns fixture data — **not live CV/OCR output**. The `is_explicit_demo` check also triggers when `PYTEST_CURRENT_TEST` environment variable is set (line 785), meaning all pytest runs bypass real pipeline.
4. **All 268 Mode B inspections not synced to central (P0-DB-001):** Every record in the Mode B SQLite database has `synced_to_central = 0`. There is no evidence the sync mechanism has ever successfully run in either direction.
5. **Missing `/close` route on live backend (P1-API-001):** `/api/v1/inspections/{id}/close` does not exist. The frontend workaround silently calls `/adjudicate` with `action_order: "CLOSE_INSPECTION_COMPLIANT"` — which is functionally and legally different.

**Current Trust Assessment:** NOT TRUSTWORTHY FOR RELIABLE INSPECTION RESULTS
**Current Demo Readiness:** READY — but for demo reasons only (fixture data, not live pipeline output)

## 4. Architecture Reality

### Documented Architecture

```
Field Camera → Upload → 12-Stage Pipeline → OCR → Rule Engine → Evidence → Report
```
With three modes: Mode A (Live PostgreSQL), Mode B (SQLite offline), Mode C (External lookups)

### Actual Architecture

```
Field Camera → Upload → api.ts (mode router)
                          ├── LIVE: liveApi.ts → FastAPI backend → pipeline/execute
                          │       ↓ if network error at ANY POINT
                          │     setOperatingMode("MOCK") [SILENT] → mockApi.ts → mockData.ts
                          │       (officer sees no difference)
                          │
                          ├── MOCK: mockApi.ts → mockData.ts (85KB hardcoded fixture file)
                          │
                          └── DEMO_FIXTURE: demoFixtures.ts → mockData.ts GOLDEN_SKU_CASES

FastAPI backend (pipeline/execute):
  ├── If matched_sku found in integration/fixtures/*.json AND is_explicit_demo
  │     → Return fixture data (NOT live CV/OCR output)
  └── Otherwise
        ├── CentralPipelineAdapter.execute_quality_gate() [if loaded]
        ├── LegalMetrologyRuleEngine.evaluate_inspection() [if loaded]
        └── If adapters failed to import → return hardcoded defaults
```

**Key Divergence:** The documented architecture shows a clean live pipeline. The actual architecture has 4 separate fallback layers, 3 of which serve synthetic data. None of the fallback activations are clearly communicated to the officer.
